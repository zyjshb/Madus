# 推荐融合：汽水音乐机制（1.22.0）

这一版把汽水音乐 PC 3.8.0 客户端里可观察到的推荐机制，按「本地可解释」的路线融进现有推荐台。
原版排序完全在服务端（`/luna/flow/*`、`/luna/feed/*`），客户端不含任何本地打分或召回代码，所以能移植的不是它的权重，
而是它的**特征口径、反馈语义和会话策略**。逆向过程与接口清单见仓库外的 `soda-music-reverse.md`。

## 一、融入了什么

| 汽水机制（原版证据） | 原来的做法 | 现在的做法 |
|---|---|---|
| 三档重复收听窗口 `[600, 3600, 86400]` 秒，配合 `played_mills` + `duration` 回传 | 只区分「听了多少秒 / 完成率」，同曲重播与认真听一遍无差别；`REPLAY` 枚举存在但从未产生 | `RecommendationFusion.repeatProfiles` 按 10 分钟 / 1 小时 / 1 天统计实际播放遍数（单曲循环按 `listenedMs / duration` 折算），真爱加分、当日疲劳扣分；`REPLAY` 接上真实重播 |
| `POST /luna/dislike` 的 body 带 `author_ids[]`，作用域是「这首歌 + 这批作者」 | 负反馈只作用于曲目/歌名，作者维度只有弱疲劳 | `RecommendationFusion.artistNegatives` 生成歌手级衰减惩罚，只压该作者，不封曲风 |
| `audio_over_status` 区分 `next` / `previous` / `hotkey_previous` / `change_track_reco` | 只有 `SKIP` 与 `SKIP_FAST` 两档，且都只看时间 | 新增 `USER_BACK(-0.95)`：按「上一首」比按「下一首」更接近否定，冷却 2 天 |
| 熟悉模式 / 新鲜模式（`preference_mode: familiar / fresh`） | 探索比例写死 25%，用户无法干预 | 三档 `TasteMode`（熟悉 / 均衡 / 新鲜），在「我的音乐口味」里直接切换并持久化 |
| 30 条上下文窗口里用 `played_mills = -1` 表达「待播」 | 重排只看已播历史与已排队 ID，补队列时接缝处可能连播同曲风/同作者 | `FeedContext.upcomingQueue` 把待播头部并进重排历史 |
| 每日 5:00 切换 + 0~1 小时随机抖动 | 无跨天锚点 | `DailyRefresh` 在 5 点后首次运行时触发一轮全量召回 |

## 二、打分变了什么

在原表达式上**只加不删**，新增项都有默认零值，均衡档下与原分数逐位一致：

```
score = 旧表达式
      + 1.0  * love                  // 十分钟内反复播放：0 / 0.20 / 0.30 / 0.55
      - 1.8  * artistNegative        // 歌手级负反馈强度，封顶 0.5 → 最多 -0.9
      + shortTermFatigue             // -min(0.25 * (当日遍数 - 3), 1.0)
      - 1.1  * anchorPenalty         // 仅熟悉模式：明确不符合画像时 1.0
      + anchorBias                   // 熟悉 +0.15 / 新鲜 -0.12，只给 liked/local/history
      + W_MISMATCH * mismatch * tasteMode.mismatchScale
```

- `W_LOVE = 1.0`、`W_ARTIST_NEGATIVE = -1.8`、`W_ANCHOR_MISMATCH = -1.1` 加在 `RecommendationTuning`。
- 疲劳与真爱会互相抵消：十分钟内循环收听算喜欢；隔一阵子反复刷的才被压。
- 歌手惩罚半衰期：明确「不合口味」30 天、快速跳过 7 天，整体封顶 0.5，不会因为一首歌废掉一个歌手。

## 三、听歌模式

| 模式 | 探索配额 | 不匹配倍率 | 熟悉加成 | 严格锚定 |
|---|---|---|---|---|
| 熟悉 | 0.08 | 1.35 | +0.15 | 是 |
| 均衡（默认） | 0.25 | 1.00 | 0 | 否 |
| 新鲜 | 0.40 | 0.50 | -0.12 | 否 |

- 探索配额换算成「每 N 位留一个探索位」，重排器上限由 0.25 放宽到 0.45。
- 熟悉模式下重排优先取池内曲目，只有没有合适候选时才用探索位；不会硬封，避免候选用尽。
- 入口显示为「我的音乐口味 · 熟悉」，模式随口味一起持久化（`MusicTasteStore.tasteMode_v1`）。

## 四、待播队列参与重排

`rankMusicPool` 把 `pendingQueue.drop(pendingIndex + 1).take(6)` 放进 `FeedContext.upcomingQueue`：

- 重排历史变成「已播 → 待播头部 → 本次新选」，跨补队列边界继续做曲风间隔（连续 2 首同曲风禁止、5 首内不超过 4 首）。
- 作者多样性会把待播头部最后 3 首的作者一并考虑，分数接近时优先换人；只有在没有更合适候选时才退回去。
- 待播曲目不携带种子信息，因此不参与「同一来源连占」的种子轮换，只影响曲风与作者。

## 五、每日刷新

`DailyRefresh.windowStartMs` 以本地时区 5:00 为界（凌晨 4:30 属于前一天窗口，跨夜听歌算前一天），
`shouldRefresh` 判断距上次刷新是否已跨过窗口起点，`jitterMs` 给出 0~59 分钟的确定性抖动。
启动并完成偏好加载后，若已跨窗口则触发一轮全量召回，其余时间沿用现有的实时自适应补池。

## 六、没有照搬的部分

- **服务端 LTR 权重**：原版 `FlowRecommendNotPack` 会返回 `{id, score}`，但打分公式在服务端，客户端拿不到。这里不猜权重。
- **曝光集回传（`exposure_radio_list`）**：原版用于卡片流防重，本项目的推荐台是单曲流，已由 `sessionSeenIds` 与 14 天已听避重覆盖。
- **`only_want` / `not_want` 硬过滤**：会与现有「一首不喜欢不封整个曲风」的契约冲突，暂不引入。
- **`reco_sample` 采样回传**：原版 PC 端也未启用（不在 `idlMethods` 白名单里）。

## 七、自动检查

```powershell
gradlew.bat :app:testDebugUnitTest --offline
```

`RecommendationFusionTest` 覆盖：三档重复窗口的真爱/疲劳判定、单曲循环按时长折算、歌手惩罚的封顶与过期、回退强于普通跳过、
三档模式对相邻曲风与探索位的影响、待播队列的曲风/作者接缝、5:00 窗口与抖动。原有 11 个测试文件全部保持通过。

## 八、人工验收建议

1. 推荐台连续听同一首两三遍，确认下一轮仍会给这首歌的作者/曲风，而不是把它判成「听腻」。
2. 当天把一首歌刷到 4 次以上、且每次都听不到一半，确认它从头几首掉下去。
3. 对某位 UP 主的歌点「不合口味」，确认同 UP 主其它歌明显后移，但同曲风的其他 UP 主仍在推荐里。
4. 播放中按「上一首」，确认这首歌进入冷却，且曲风没有被整体压掉。
5. 在「我的音乐口味」里切到「新鲜」，确认推荐里陌生歌手/相邻曲风变多；切回「熟悉」后回到已验证方向。
6. 连续切歌到队列中后段，检查补队列的接缝处不出现连续两首同曲风。

## 九、边界

- 作者身份取 UP 主名称（`ContentProfile.authorKey`），改名或搬运号会让歌手惩罚失真。
- 重复遍数依赖 `listenedMs / duration`，时长缺失（`durationMs <= 0`）时按 1 遍计。
- 最热门的极端情况：一首歌十分钟内被循环 5 遍以上，真爱加分与当日疲劳可能相互抵消，此时以疲劳项为准。
- 每日刷新只用进程内时间戳，重启后 5 点窗口内可能再刷新一次；这是刻意的取舍，避免多写一份持久化状态。
